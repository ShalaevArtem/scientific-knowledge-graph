# Как устроена система — внутренний гид для защиты

Документ для команды: точное устройство всех слоёв + заготовки ответов на вероятные
вопросы жюри. Всё ниже — из актуального кода, с путями к файлам.

---

## 1. Общая архитектура

**GraphRAG над единственным хранилищем Neo4j (Community Edition).** В одной БД живут:

- граф знаний (узлы/рёбра по онтологии),
- векторный индекс `chunk_embedding` (384 измерения, cosine),
- полнотекстовый индекс `chunk_search` (Lucene, русский анализатор → BM25).

Никакого Elasticsearch/Qdrant — меньше движущихся частей, один бэкап, одна транзакционность.

Поток данных:

```
корпус (PDF/DOCX/PPTX/XLS/XLSX + OCR)
  → skg ingest   (Document + Chunk, provenance до страницы/слайда/листа)
  → skg embed    (локальные эмбеддинги fastembed/ONNX, без GPU и внешних API)
  → skg extract  (LLM по онтологии → сущности, измерения, выводы; needs_review)
  → слой запросов (вопрос → фильтры → гибридный поиск 4 канала → RRF → сводка LLM)
  → веб-UI (FastAPI + один HTML: поиск, граф, пробелы, review, статистика, аудит)
```

Два инварианта:
1. **Provenance**: каждое извлечённое ребро несёт `source` (id чанка), `unit`
   (страница/слайд), `confidence`, `extracted_at`, `model`. «Нет источника — нет факта».
2. **Верификация**: всё, что впервые извлечено LLM из текстов, получает
   `needs_review = true` и видно в очереди эксперта (`/api/review`). Seed-справочники
   считаются верифицированными.

## 2. Ингест корпуса (`src/skg/ingest/`, `src/skg/loaders/corpus.py`)

### Реестр (`registry.py`)
- Метаданные — из структуры папок выгрузки кейса: `Источники информации/<Категория>/…`.
  Категории: Доклады → «доклад», Журналы → «журнальная статья» (+ имя журнала и год
  из пути), Материалы конференций, Обзоры, Статьи.
- `doc_id` = `"D" + sha1(rel_path)[:12]` — детерминированный, повторный ingest идемпотентен.
- Год — regex 1950–2029 по имени файла/папки; автор доклада — из имени файла
  `Доклад_<ФИО>.pdf`.
- Язык — эвристика: доля кириллицы в первых 4000 символов > 0.4 → `ru`, иначе `en`.

### Извлечение текста (`textract.py`)
- **PDF** — PyMuPDF (fitz), юнит = страница. Если на странице < 20 символов текста и есть
  картинки — это скан: при `SKG_OCR=1` страница рендерится в 300 DPI и распознаётся
  Tesseract (rus+eng, языковые данные в локальном `.cache/tessdata`).
- **DOCX/DOCM** — python-docx, юнит = блок из 40 абзацев; таблицы добавляются построчно
  через « | ». Для macro-enabled DOCM подменяется content-type в `[Content_Types].xml`
  (python-docx иначе отказывает).
- **PPTX** — python-pptx, юнит = слайд (текстовые фреймы + таблицы).
- **XLSX/XLSM** — openpyxl (read_only + data_only: значения формул, не формулы),
  **XLS** — xlrd. Юнит = лист, лимиты 5000 строк / 200 000 символов на лист.
- Битый файл → `ExtractionError`, попадает в отчёт отклонённых, пайплайн не падает.

### Чанкинг (`chunker.py`)
- ~1200 символов, перекрытие 150; резка по границе предложения/абзаца.
  Размер согласован с лимитом эмбеддинг-модели (512 токенов).
- `chunk_id = "{doc_id}:{seq}"`; чанк хранит `unit_kind`/`unit_no` — этого достаточно,
  чтобы человек нашёл цитату в оригинале.
- При повторном ingest (например, с OCR) если текст чанка изменился — эмбеддинг
  обнуляется, `skg embed` пересчитает только их.

## 3. Эмбеддинги (`src/skg/embeddings.py`)

- **fastembed (ONNX Runtime)**, модель `paraphrase-multilingual-MiniLM-L12-v2`,
  384 измерения, мультиязычная (RU/EN). Полностью локально: без GPU и внешних API —
  377 тысяч чанков не стоили ни рубля.
- `skg embed` возобновляем: берёт только чанки с `embedding IS NULL`; журнальные
  подшивки (самая объёмная часть) эмбеддятся в последнюю очередь.
- Вектор пишется через `db.create.setNodeVectorProperty`, индекс — HNSW-подобный
  векторный индекс Neo4j.
- ⚠️ Нюанс: комментарий в `schema/003_corpus.cypher` упоминает `e5-small` — это
  устаревшая строка, фактическая модель задаётся `EMBED_MODEL` в env; размерность
  та же (384), поэтому индекс валиден.

## 4. LLM-извлечение (`src/skg/extract/`)

### Клиент (`llm.py`)
- Три провайдера за одним интерфейсом: **Anthropic**, **Yandex AI Studio** (нативный
  API `foundationModels/v1/completion`), любой **OpenAI-совместимый** (с
  `response_format: json_object`). Конфиг — `.env`: `LLM_PROVIDER/MODEL/API_KEY`
  (+ `LLM_FOLDER_ID` для Яндекса). На кейсе использовался Yandex AI Studio.
- Ретраи: 4 попытки с экспоненциальной паузой на 429/5xx/сетевые ошибки.
- `complete_json`: невалидный JSON → один повторный запрос с требованием «строго JSON»;
  срезаются markdown-заборы, берётся подстрока от первой `{` до последней `}`.
- Роли моделей: `extract` (дешёвая, массовое извлечение) и `synth`
  (`LLM_MODEL_SYNTH`, для сводок; по умолчанию та же).

### Схема результата (`schema.py`, pydantic)
Из чанка извлекаются: materials, processes, equipment, facilities (со страной),
measurements (property/value/value_max/unit/conditions), conclusions
(text/materials/processes/geography/confidence), topics (из фиксированного списка),
authors (только с титульных фрагментов — не из списков литературы).

Защита от слабых моделей (весь «грязный» JSON нормализуется до записи):
- строки вместо объектов → коэрсятся (`"никель"` → `{"name": "никель"}`);
- `"Nikkelverk (Норвегия)"` → name + country;
- значения-строки парсятся: `«60°C»` → (60, unit «°C»), `«200–240»` → диапазон
  value/value_max (различаются дефис диапазона и минус «-0,25»);
- **измерение с непарсимым числом отбрасывается целиком** — числа не выдумываются.
  Это и есть ответ на требование «ошибки в концентрациях недопустимы».

### Запись в граф (`extractor.py`)
- Чанки обрабатываются волнами по 300: LLM-вызовы параллельно (ThreadPoolExecutor,
  на кейсе workers=6 при лимите Яндекса ~10 одновременных), запись — последовательно.
  Падение процесса теряет максимум одну волну; ошибка одного чанка не валит прогон.
- **Нормализация**: упоминания разрешаются в канонические узлы по нормализованному
  имени и синонимам (словарь строится из графа, куда `skg seed` загрузил
  `data/seed/*.csv` — канонические Material/Process/Equipment с RU/EN-синонимами).
  Так «ПВП», «печь взвешенной плавки» и «flash furnace» — один узел.
  Неизвестное имя → новый узел с `needs_review = true`.
- Рёбра: `MENTIONS` (count инкрементируется), `REPORTS → Measurement → OF_PROPERTY →
  Property`, `Conclusion → DESCRIBED_IN → Document` и `ABOUT → Material/Process`,
  `TAGGED → TopicTag`, `AUTHORED_BY → Person`.
- Вывод с `confidence < 0.6` дополнительно помечается `needs_review`.
- Обработанный чанк получает `extracted_at` — извлечение возобновляемо.

### Версионирование фактов
При повторном извлечении (`skg extract --force`) если text/confidence/geography вывода
изменились — прежнее состояние архивируется в узел `ConclusionVersion`
(ребро `HAD_VERSION`), у актуального узла `version += 1`, `updated_at` обновляется.
История доступна через `GET /api/conclusion/history?id=…`. Ничего не затирается молча.

### Широтная стратегия прогона (важно для честных ответов)
Бюджет API не позволял прогнать все 377 тысяч чанков (~5–6 тыс. чанков/час).
Поэтому `infra/extract_breadth.py` выбирал чанки **stride-ом ~20 на документ** по всем
документам — покрыты все категории и весь корпус «вширь» (~29 тыс. чанков), но не каждый
чанк. Добор до полной глубины — просто повторный запуск, архитектура не меняется.
~0.4 % чанков модель не разобрала даже с ретраями.

## 5. Слой запросов (`src/skg/query/`)

### Гибридный поиск — 4 канала → RRF (`search.py`)
1. **Вектор** — `db.index.vector.queryNodes`, ловит перефразировки и RU/EN.
2. **BM25** — `db.index.fulltext.queryNodes` (русский анализатор), ловит точные
   термины/марки/формулы; спецсимволы Lucene экранируются.
3. **Граф** — канонические сущности (Material/Process/Equipment), лексически
   распознанные в вопросе (свой лёгкий стеммер: срез окончаний до 2 символов +
   ограничение длины хвоста — «электроэкстракции» ≈ «электроэкстракция», но
   «мед» ≠ «медленный»). Через рёбра `MENTIONS` находятся документы, покрывающие
   **несколько** сущностей сразу (need ≥ 2 при двух и более сущностях), их
   чанки-источники (provenance рёбер) — третий список кандидатов. Так запрос
   «материал + процесс» отвечается структурой графа, а не только текстовой близостью.
4. **Измерения** — числовые ограничения из вопроса («сульфаты ≤ 300 мг/л») матчатся
   на узлы Measurement: показатель — стеммингом по именам Property, значение —
   **пересечением интервалов** (у измерения диапазон value..value_max, у ограничения
   интервал из оператора; «=» — с допуском ±10 %), единицы сверяются после нормализации
   («мг/дм³» ≡ «мг/л»). Чанки ранжируются по числу удовлетворённых ограничений.

Слияние — **Reciprocal Rank Fusion** (`score = Σ 1/(60 + rank)`): не требует калибровки
скорингов между разнородными индексами. Берётся `fetch_k = max(k*5, 40)` кандидатов.

Пост-обработка выдачи:
- фильтры по метаданным документа (категория, язык, годы) — в Cypher при выборке;
- **диверсификация**: максимум 2 чанка одного документа в топе;
- **дедуп перепечаток**: сигнатура текста (первые 420 нормализованных символов) —
  одинаковые статьи из разных выпусков журнала не дублируются;
- у журнальных PDF метаданные-титулы вида «CM_7_03.qxd» заменяются на
  «Цветные металлы, 2003».

### Ответ на вопрос (`answer.py`)
1. **Разбор вопроса** (LLM → JSON): переформулированный запрос, year_from/to
   («за последние 5 лет» — от текущего года), язык, категория, география,
   constraints (property/op/value/value_max/unit). Только явные ограничения,
   числа не пересчитываются. Явные фильтры из UI имеют приоритет над распознанными.
2. Гибридный поиск (все 4 канала).
3. **Синтез** (LLM): правила промпта — каждое утверждение с [n]-цитатой («без ссылки —
   не утверждай»), числа точно как в источнике с единицами, расхождения источников
   показывать явно, различать практику РФ/мира, честно говорить «данных мало»,
   структура «краткий вывод → детали → Пробелы/что уточнить».
4. **Деградация без ключа**: LLM нет → тот же гибридный поиск, фрагменты с источниками,
   просто без сводки. Система не ломается.

## 6. Веб-слой (`src/skg/web/`)

FastAPI + один статический HTML (vanilla JS). Вкладки: **Поиск/Ответ**, **Граф**,
**Пробелы**, **Очередь review**, **Статистика**, **Аудит** (только админ).

Вкладки: **Поиск/Ответ**, **Граф**, **Пробелы**, **Дашборд** (руководитель),
**Очередь review**, **Статистика**, **Аудит** (только админ). Дашборд и Аудит
показываются в навигации по флагам из `/api/whoami`.

Ключевые эндпоинты:
- `GET /api/answer?q=…` — полный цикл вопрос→ответ с цитатами и фильтрами.
- `GET /api/search` — гибридный поиск без синтеза.
- `GET /api/context?chunk_id=…` — фрагмент ± 2 соседних чанка + путь к файлу
  (клик по цитате [n]).
- `GET /api/graph?doc_id=…` или `?label=…&key=…` — окрестность документа/сущности
  (топ-15 документов, топ-8 соседних сущностей каждого).
- `GET /api/gaps` — матрица «материал × процесс» по числу документов, только
  верифицированные сущности; топ-20 × топ-20.
- `GET /api/dashboard` — сводка руководителя (см. §6.1). Внутренние роли.
- `GET /api/experts?topic=…` — гибридный поиск по теме → авторы найденных документов.
- `GET /api/entity/{label}/{key}` — карточка сущности: документы, выводы.
- `GET /api/review` — очередь needs_review (закрыта для внешних).
- `POST /api/review/{approve|edit|comment|reject}` — действия эксперта над узлом (см. §6.2).
- `GET /api/conclusion/history?id=…` — версии вывода.
- `GET /api/stats`, `GET /api/health`, `GET /api/whoami`, `GET /api/audit`.

### 6.1 Дашборд руководителя (`/api/dashboard`)
Агрегирует уже существующие данные графа в срез для принятия решений (не заводит новых
сущностей). Возвращает четыре блока:
- **KPI**: документы, выводы, измерения, сущности, «проверено экспертом», «ждут проверки».
- **Покрытие по направлениям** — документы/выводы/измерения на каждый `TopicTag`.
  ⚠️ Наивная версия запроса (conclusions × measurements на документ) деградировала до ~24 с
  на реальном корпусе из-за декартова произведения; в рабочей версии счётчики схлопываются
  по документу до следующего расширения → **0,3 с**. Если спросят про производительность
  дашборда — это конкретный пример оптимизации Cypher.
- **Зоны риска** — пары «материал × процесс» с 1–3 источниками (в отличие от нулевых
  «неизученных» на вкладке «Пробелы»): слабо подтверждённые темы, кандидаты на НИР.
  Клик по чипу открывает поиск по паре.
- **Носители экспертизы** — авторы по числу документов.
Прогресс верификации = reviewed / (reviewed + needs_review); растёт по мере работы эксперта.

### 6.2 Ручная корректировка графа экспертом (`POST /api/review/{op}`)
Очередь `needs_review` раньше только читалась — теперь эксперт действует над узлом.
Одно тело запроса `{label, key, name?, text?, geography?, synonyms?, note?}`, `op`:
- **approve** — `needs_review=false`, `review_status='approve'`, пишет `reviewed_by`
  (имя из токена) и `reviewed_at`. Узел становится верифицированным → входит в разрешение
  сущностей и в тепловую карту пробелов.
- **edit** — правит поля (сущность: `name`, `synonyms`; вывод: `text`, `geography`) и
  подтверждает (`review_status='edit'`).
- **comment** — добавляет строку `«автор (дата): текст»` в список `review_notes`;
  статус верификации **не** меняет.
- **reject** — `DETACH DELETE` узла: явное удаление ошибочного извлечения (галлюцинации).
  В UI — с `confirm()`.
Каждое действие пишется в `logs/audit.jsonl` (`review_approve`/`_edit`/`_comment`/`_reject`).
RBAC: `can_edit_graph` = роль ≠ «внешний партнёр»; кнопки в UI показываются по флагу из
`/api/whoami`, а на сервере действие защищено `_require_editor` (403 для внешних).
Валидация: неизвестный `op` → 400, отсутствующий узел → 404.

### RBAC и аудит (`auth.py`)
- 5 ролей: исследователь, аналитик, руководитель проекта, администратор, внешний партнёр.
- Токены — JSON в `AUTH_TOKENS` (.env), заголовок `X-Auth-Token`. Без токенов —
  открытый режим с ролью `AUTH_OPEN_ROLE` (по умолчанию researcher; `deny` → 401).
- **Внешний партнёр не видит** категории «обзор» и «доклад» (внутренние материалы НИИ):
  фильтр `allowed_categories` прошит в Cypher поиска, в просмотр контекста и в граф.
  Ему также недоступны дашборд, очередь review и корректировка графа
  (`can_view_dashboard` / `can_edit_graph` = роль ≠ external).
- **Аудит**: каждый запрос данных — строка в `logs/audit.jsonl` (UTC, пользователь,
  роль, действие, параметры). Просмотр — вкладка «Аудит» у администратора.
  Действия эксперта (approve/edit/comment/reject) и просмотр дашборда тоже логируются.

## 7. Схема Neo4j (`schema/*.cypher`)

- `001` — уникальность ключей (Material.id, Document.id, Conclusion.id, Regime.key —
  детерминированный хэш параметров режима, и т.д.). NOT NULL в Community недоступен —
  обязательность полей валидируют pydantic-модели загрузчиков.
- `002` — диапазонные индексы (даты, значения измерений, температуры режимов) +
  полнотекстовые с русским анализатором (материалы по маркам/синонимам, заголовки,
  тексты выводов).
- `003` — расширение под корпус: constraints для Process/Facility/TopicTag/Chunk,
  индексы по category/year/language/country, `chunk_search` (BM25) и `chunk_embedding`
  (vector, 384, cosine).
- `004` — индексы версионирования (ConclusionVersion).

13 типов узлов: Material, Process, Equipment, Facility, Document, Chunk, Property,
Measurement, Conclusion, Experiment, Regime, Person, TopicTag (+ служебный
ConclusionVersion). Experiment/Regime — из структурированных загрузчиков этапа 1
(CSV/JSONL: `skg load`, `skg load-all`), с рёбрами USES/APPLIES/ON_EQUIPMENT/YIELDS/LEADS_TO.

| Чанк | ~1200 символов, перекрытие 150 |
| Эмбеддинги | multilingual MiniLM-L12-v2, 384d, локально (fastembed/ONNX) |

## 9. Вероятные вопросы жюри — заготовки ответов

**Почему Neo4j для всего, а не Elasticsearch + отдельная векторная БД?**
Neo4j 5+ умеет и векторный, и полнотекстовый (Lucene, русский анализатор) индексы.
Одно хранилище = одна транзакционность, один бэкап, нет синхронизации между системами.
Требование производительности (3–5 с при 1 млн сущностей) выполняется на индексах:
у нас 377 тыс. чанков и ~3 с. Если корпус вырастет на порядок — поисковый движок
подключается как ещё один канал RRF без переделки архитектуры.

**Как гарантируете точность чисел (требование «ошибки недопустимы»)?**
Тройная защита: (1) при извлечении промпт запрещает выдумывать числа, а pydantic-валидатор
отбрасывает измерение целиком, если число не парсится; (2) при синтезе промпт требует
цитировать числа точно как в источнике с единицами и ссылкой [n]; (3) пользователь
всегда может кликнуть цитату и увидеть исходный фрагмент ± 2 абзаца. Число никогда
не существует в системе без пути к первоисточнику.

**А если LLM галлюцинирует сущности?**
Неизвестные сущности не смешиваются с каноном: они создаются с `needs_review = true`
и видны в очереди эксперта. Поиск сущностей в вопросе и тепловая карта пробелов работают
только по верифицированным узлам. Плюс на каждом ребре — confidence и модель.

**Как работает «сульфаты ≤ 300 мг/л»?**
Разбор вопроса даёт структурированное ограничение (property/op/value/unit). Показатель
матчится на канонические Property стеммингом, значение — пересечением интервалов
(измерение само может быть диапазоном), единицы нормализуются («мг/дм³» ≡ «мг/л»).
Чанки с подходящими измерениями входят четвёртым каналом в RRF — то есть числовое
ограничение влияет на ранжирование документов, а не просто фильтрует постфактум.

**Почему RRF, а не взвешенная сумма скорингов?**
Скоринги каналов несравнимы (cosine ∈ [0,1], BM25 неограничен, граф — счётчики).
RRF работает только с рангами — без калибровки и обучения, устойчив и предсказуем.

**Мультиязычность?**
Три уровня: мультиязычная эмбеддинг-модель (вопрос по-русски находит английский текст),
RU/EN-синонимы в канонических узлах («электроэкстракция» ≡ «electrowinning»),
поле `name_en` при извлечении. Язык документа — отдельный фильтр.

**Отечественная vs зарубежная практика?**
География живёт в данных: `Facility.country`, `Conclusion.geography` («РФ» / «зарубежная»
/ страна). Разбор вопроса распознаёт географию, промпт синтеза обязан разделять практику
РФ и мира. Жёсткий Cypher-фильтр по географии на уровне выдачи — прямое расширение
(поле уже индексируемо), сейчас разделение делается на уровне выводов и синтеза.

**Версионирование фактов?**
`skg extract --force`: изменившийся вывод архивируется в ConclusionVersion (HAD_VERSION),
version инкрементируется, история — `/api/conclusion/history`. Изменение не затирает
прошлое молча — видно, какая модель и когда изменила формулировку.

**Масштабируемость на новые домены?**
Онтология «упоминание-центричная», без жёсткой схемы: новый домен = новая папка корпуса
(категория) + при желании новые seed-термины. Миграций не нужно — Neo4j schemaless,
constraints только на уникальность ключей. Новые типы сущностей добавляются меткой.

**Почему извлечение не по всем чанкам?**
Бюджет общего ключа API. Выбрали широту вместо глубины: stride ~20 чанков на документ
по всем 1965 документам — каждая тема корпуса представлена в графе. Добор до 100 % —
повторный запуск той же команды, всё возобновляемо (`extracted_at` на чанке).

**Что со связями SUPPORTS/CONTRADICTS?**
Для структурированных источников (этап 1) — есть в модели. Между выводами из текстов —
пока вручную/в road map: нужна попарная LLM-сверка выводов одного показателя, это
следующий шаг после полной глубины извлечения. Расхождения источников уже сейчас
показываются в тексте ответа (требование промпта синтеза).

**Эксперты — откуда?**
Авторы: из имён файлов докладов («Доклад_<ФИО>») и LLM-извлечения титульных фрагментов
(из списков литературы авторов брать запрещено промптом). `/api/experts`: гибридный
поиск по теме → авторы найденных документов, ранжированные по числу документов.

**Как эксперт правит граф? (ручная корректировка)**
Вкладка «Проверка» показывает очередь `needs_review`. У каждого элемента — четыре действия:
подтвердить, править (имя/синонимы для сущности; текст/география для вывода),
прокомментировать, удалить ошибочное извлечение. Подтверждение/правка снимают
`needs_review` и пишут `reviewed_by` + `reviewed_at`; комментарий добавляет дату+автора
в `review_notes`; удаление — `DETACH DELETE`. Всё логируется в аудит. Внешним партнёрам
недоступно. Это замыкает требование «модель верификации знаний»: факт извлечён → помечен →
подтверждён человеком с фиксацией кто/когда.

**Что показывает дашборд руководителя?**
Покрытие знаний по направлениям (документы/выводы/измерения на `TopicTag`), зоны риска
(пары «материал × процесс» с 1–3 источниками — слабо подтверждённые темы), прогресс
верификации (доля проверенного экспертом) и носителей экспертизы. Всё — агрегация того,
что уже в графе, отдельного хранилища метрик нет. Загрузка < 1 с (см. §6.1 про
оптимизацию тяжёлого запроса покрытия с 24 с до 0,3 с).

**Что будет без LLM-ключа?**
Всё, кроме извлечения и сводок: ingest, эмбеддинги, гибридный поиск, граф, пробелы,
статистика, дашборд, корректировка графа. `/api/answer` вернёт фрагменты с источниками
без синтеза — graceful degradation.

**Надёжность импорта?**
Битые файлы → отчёт отклонённых с диагностикой, пайплайн живёт. DOCM с макросами
читается через подмену content-type. XLS-книги с тысячами строк усечены лимитами.
Сканы — OCR (опционально, `SKG_OCR=1`). Всё идемпотентно (MERGE по детерминированным id).

**Производительность при 1 млн сущностей?**
Все горячие пути — по индексам: vector (approximate NN), fulltext, range-индексы
по метаданным, уникальные ключи. Кандидатные списки ограничены (fetch_k, LIMIT 15
у графового канала, LIMIT 5000 у измерений). Рост корпуса → те же O(log n) по индексам.

**Безопасность?**
RBAC (5 ролей из ТЗ), закрытые категории для внешних прошиты в Cypher (не в UI),
анонимный режим отключаем (`AUTH_OPEN_ROLE=deny`), полный аудит действий в JSONL.

## 10. Слабые места — знать заранее (не озвучивать первыми)

1. **Стеммер сущностей самодельный** (срез окончаний) — возможны редкие ложные матчи;
   компенсируется ограничением длины хвоста и тем, что это лишь один из четырёх каналов.
2. **География не является жёстким фильтром выдачи** — разделение на уровне данных
   выводов и промпта синтеза (честный ответ: «поле индексировано, фильтр — очевидное
   расширение»).
3. **Комментарий в схеме про e5-small** устарел (фактическая модель MiniLM, тоже 384d).
4. **SUPPORTS/CONTRADICTS из текстов** не автоматизированы (слайд 10 говорит об этом сам).
5. **Экспорт** — только Markdown (PDF/JSON-LD в road map).
6. **Уведомления/подписки** — не реализованы (слайд 10). Дашборд руководителя —
   **реализован** (§6.1), обновить формулировку слайда 10, если о нём зайдёт речь.
7. `confidence = 0.8` у MENTIONS-рёбер — константа извлечения, а не калиброванная
   вероятность; у Conclusion — оценка категоричности утверждения моделью.
8. **Reject удаляет узел безвозвратно** (`DETACH DELETE`) — версионирования удалений нет;
   для демо это осознанный выбор (чистка галлюцинаций), в проде разумно перейти на
   мягкое удаление с архивом. В UI стоит `confirm()`.
